# eufy体重計 BLEプロトコル調査資料

## 目的と読み方

eufy体重計のBLE通信について、機種別のGATT構成、送信コマンド、通知形式、
認証、履歴転送をまとめます。特定のクライアント実装や保存方式には依存しません。

判明した送受信形式、接続手順、機種差、認証、履歴処理をまとめ、
未解読のフィールドや実機未確認の動作も明示します。「記載がある」ことは
「すべてのファームウェアで動作確認済み」を意味しません。

| 資料 | 内容 |
| --- | --- |
| [T9120 / T9146 / T9146 C1 / T9147](protocol/t9120.md) | CF測定、履歴、日時、単位、safe mode |
| [T9140 V1 / V2 / V3](protocol/t9140.md) | AC 02フレーム、variant判定、結合通知、履歴、ACK、旧版との差 |
| [T9148 / T9149](protocol/t9148.md) | 複数通知チャネル、測定、心拍、分割データ、設定・履歴 |
| [T9150 / T9130](protocol/t9150.md) | 3チャネル、分割データ、ユーザー選択、履歴 |
| [共通認証と暗号化](protocol/authentication.md) | MAC由来鍵、AES-CBC、C0〜C3、C6、分割形式と検算例 |

最初にこのページで通信ファミリーを確認し、機種別資料を参照してください。
T9148/T9150系については認証資料も必要です。

## 確認状況

| 区分 | 意味 |
| --- | --- |
| 解析確認 | 送信生成処理と受信処理から確認した形式。全機種・firmwareでの相互接続は未確認です。 |
| 実測記録 | T9120の既存記録。今回、新たな実機通信は行っていません。 |
| 合成例・検算例 | 数値変換やchecksum等を確認するために作成したbyte列です。 |
| 未確認 | 未解読フィールド、未確認の応答・機種差などです。 |

## 通信ファミリーとGATT早見表

短縮UUID `FFF0` 等は、特記しない限り
`0000xxxx-0000-1000-8000-00805f9b34fb` を表します。
Nは通知を受信するcharacteristic、Wは書き込み先です。

| ファミリー | 製品識別名 | service | characteristic |
| --- | --- | --- | --- |
| A | `eufy T9120`, `eufy T9146`, `eufy T9146 C1`, `eufy T9147` | `FFF0` | N=`FFF4`, W=`FFF1` |
| B V1 | `eufy T9140` | `FFB0` | N=`FFB2`, W=`FFB1` |
| B V2 | `eufy T9140`、内部識別`eufy T9140_V2` | `4143f6b0-5300-4900-4700-414943415245` | N=同形式`f6b2`, W=同形式`f6b1` |
| B V3 | `eufy T9140`、内部識別`eufy T9140_V3` | `4143f7b0-5300-4900-4700-414943415245` | N=同形式`f7b2`, W=同形式`f7b1` |
| C | `eufy T9148`, `eufy T9149` | `FFF0` | N=`FFF4`と`FFF2`, W=`FFF1` |
| D | `eufy T9150`, `eufy T9130` | `FFF0` | N=`FFF1/FFF2/FFF3`, W=`FFF1`制御・`FFF2`認証/データ |

DのFFF1は通知専用ではなく、通常の制御コマンドも書き込むcharacteristicです。
認証・データ用のFFF2とは分けて扱います。

この表は接続後のGATT構成です。同じUUIDが必ず広告に含まれる証拠ではありません。
FFF0だけではA/C/Dや別製品を区別できません。T9140は同じlocal nameを使い、
広告内のvariant情報で分岐します。詳細は機種別資料を参照してください。

## 検出と接続

local nameと接続後のGATT構成を組み合わせてファミリーを識別します。
T9140のvariant判定は機種別資料に記載します。サービスUUIDが広告に常に含まれるとは
限らず、FFF0だけで通信形式を確定することもできません。

接続後は必要な通知characteristicを購読し、機種別の初期化に進みます。
T9148/T9149とT9150/T9130は複数の通知チャネルと認証を使います。
T9150/T9130ではMTU拡張要求も行われます。具体的な購読順と送信先は各資料を参照してください。
scan周期、接続timeout、再接続方針はクライアント側の動作であり、共通wire仕様ではありません。

## 数値・表記の約束

- オフセットは0始まり、`3..4`は両端を含むbyte範囲です。
- LE16/LE24/LE32はunsigned little-endian整数、BE16はunsigned big-endianです。
- hexの空白は読みやすさのためで、通信に空白文字を含めません。
- XORは指定範囲の排他的論理和、SUM8はbyte和の下位8 bitです。
- 送信templateと完成フレームを区別します。checksum追加前の定数を完成形とは扱いません。
- 体重のraw値と表示単位を分けます。A/C/Dは主な測定値をraw / 100 kg、
  Bはraw / 10 kgとして解釈します。表示単位変更の実機影響は別途未確認です。
- encrypted impedanceは解析元の意味づけを引き継いだ呼称です。
  値を読めることは、体組成演算やその復号を再現できることを意味しません。

## 実測・検証の現在地

引き継いだ実測情報はT9120の記録だけです。接続、FFF4購読、初期化後に同一stable通知を
2回受信し、53.00 kgと解釈、その後f3 00と切断を記録しています。履歴は取得されていません。
元キャプチャ、時刻付き全送受信列、ファームウェア情報を今回再確認していないため、
詳細は[T9120の旧実測記録](protocol/t9120.md#旧実測記録)にまとめています。

他ファミリー、認証、履歴、心拍、設定、OTA/DFUは通信処理の解析に基づく記述で、
本改訂では実機通信を行っていません。暗号・checksumの検算と実機との相互接続試験は別です。

| 論点 | 残る不確実性を減らすために必要な観測 |
| --- | --- |
| 機種・版の互換性 | 製品名、広告全体、GATT一覧とproperties、ファームウェア版 |
| 接続と初期化 | 接続/CCCD/write完了/notify/切断を同一時計で記録した系列 |
| 履歴 | 履歴を持つ状態での要求、各record、完了応答、時刻と件数の照合 |
| 表示単位 | 同じ荷重でkg/lb/stを変更した前後のrawと本体表示 |
| 完了と重複 | 動的値、安定体重、体組成・心拍完了、同一通知の再送 |
| 認証 | MACの由来、購読先別のC0〜C3/C6、分割、失敗応答、再接続 |

履歴削除や設定変更は単なる読み取りではありません。送信形式を載せていることと、
測定値を読む際にすべて送る必要があることは同義ではありません。
それぞれの送信条件は機種別資料に記載します。
