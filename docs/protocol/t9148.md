# T9148 / T9149

[全体索引・確認状況](../protocol.md)

## 対象と確認状況

T9148/T9149系は、`FFF0` serviceに通常通知と追加通知を持つBLE体重計プロファイルです。
ここではGATT、送受信byte列、分割、測定・履歴・Wi-Fi listの配置を記載します。
認証・AES・C1/C2/C3の交換は[共通認証と暗号化](authentication.md)へ分離しています。

T9149はT9148と同じプロファイル候補として扱われていますが、T9149の実機で同一の
packetになることは確認できていません。本資料は固定版アプリの通信処理から復元した
仕様であり、メーカーの公開仕様書でも、T9148/T9149の実機キャプチャでもありません。
実機で未確認の項目は明示します。

## 検出とGATT

短縮UUIDは、特記しない限り
`0000xxxx-0000-1000-8000-00805F9B34FB`へ展開します。

| 役割 | UUID | 使い方 |
| --- | --- | --- |
| service | `0000FFF0-0000-1000-8000-00805F9B34FB` | 主service |
| primary notify | `0000FFF4-0000-1000-8000-00805F9B34FB` | 最初に通知購読 |
| write | `0000FFF1-0000-1000-8000-00805F9B34FB` | 認証、制御、データ送信 |
| 追加notify | `0000FFF2-0000-1000-8000-00805F9B34FB` | 追加通知。packet種別との厳密な対応は未確認 |
| device information service | `0000180A-0000-1000-8000-00805F9B34FB` | firmware revision read |
| firmware revision | `00002A26-0000-1000-8000-00805F9B34FB` | version値 |
| battery service | `0000180F-0000-1000-8000-00805F9B34FB` | battery read |
| battery level | `00002A19-0000-1000-8000-00805F9B34FB` | battery値 |

## 接続と初期化

接続後の基本順序は次の通りです。

1. `FFF0` serviceをdiscoverする。
2. `FFF4`をnotifyとして有効化する。
3. `FFF1`を書き込みcharacteristicとして保存する。
4. `FFF4`のCCCD書き込み成功後、`FFF2`を追加notifyとして有効化する。
5. `FFF2`のCCCD書き込み成功後、認証を開始する。
6. 認証を`FFF1`で完了し、必要な制御・測定要求を送信する。

T9148はMTU拡張を要求せず、通常のBLE service discoveryへ進みます。接続時に
アプリ側へconnected状態が通知されても、追加通知の購読と認証が完了したとは限りません。

`FFF2`を追加通知として開くことはこのプロファイルの特徴ですが、受信packetの
characteristic UUIDだけで認証packetと測定packetを区別できるとは限りません。受信処理は
UUIDより先頭byteを優先する実装になっているため、`FFF2`だけが認証通知であると固定
しないでください。

### 認証後の初期化例

登録済み機器へ接続した際に確認した送信スケジュールです。時間は認証成功からの
コマンド送信予約時刻で、機器が要求する最小待ち時間ではありません。

| 認証成功から | コマンド | 条件・用途 |
| --- | --- | --- |
| 200 ms | 単位設定 | 保存済み単位 |
| 600 ms | 時刻同期 | UTC暦日時 |
| 1000 ms | safe mode設定 | 保存済み設定に従う |
| 1400 ms | 心拍open/close | T9149の場合のみ |
| 1800 ms | 履歴要求 | F2 01 00 |
| 2200 ms | bind状態取得、またはdevice informationのread | 接続設定によって分岐 |
| 2600 ms | token状態取得 | bind状態取得側の経路のみ |

履歴はC6を再構成したCF recordで受信し、F2の完了通知で一区切りになります。
確認したクライアントは、履歴を1件以上受信した場合だけ履歴削除を要求します。
削除要求は通常の読み取りとは別操作です。

## 送信フレーム

### XOR

XORには2種類あります。

- **body checksum**: 一部のbodyへ、body全byteのXORを1 byte追加する。
- **fragment XOR**: 分割frameの先頭からpayload末尾までのXORを末尾へ追加する。

例えば単位kgのbody `FD 0A 00 00 00 00 00 00 00 00 00`へ追加するbody checksumは`F7`です。受信側がchecksumを検証するとは
限らないため、送信時の規則を受信packet全体の検証規則へ一般化しません。

### C6分割

短いbodyはC6 frameへ入れます。入力bodyを30 hex文字ずつ、つまり最大15 byteずつに
分割します。

```text
C6 | fragment_count | fragment_index | total_body_bytes |
body_fragment | fragment_xor
```

`fragment_count`はfragment総数（1以上）、`fragment_index`だけが0始まりです。
`total_body_bytes`は分割前bodyのbyte数であり、各fragmentで共通します。
`fragment_xor`は`C6`からbody fragment末尾までを対象にします。body自体のchecksumを
付けるかどうかはコマンドごとに異なります。

例えばchecksumを持たないbody `F2 01 00`を1 fragmentで送ると、合成例は次の通りです。

```text
body       F2 01 00
C6 frame   C6 01 00 03 F2 01 00 37
```

最後の`37`はframe全体のXORです。この値は計算例であり、実機ログではありません。

### 長いデータの分割

コード、証明書、Wi-Fi名・password、tokenなどは、まず最大53 byteのinner fragmentへ分割
します。inner fragmentは直接writeせず、各inner frameをさらにC6 frameで包む二重分割
です。

```text
head | fragment_length | fragment_count | fragment_index |
original_body_bytes(LE16) | body_fragment | inner_fragment_xor
```

`fragment_length`の値はinner payloadに5 byteを加えた長さで、inner frame全体はpayload
に7 byteを加えた長さです。`original_body_bytes`は元データのbyte数をLE16で持ち、
head、length、count、indexは各1 byteです。headは`F8`、`F7`、`0A`、`0B`、`B2`など、
データ種別ごとに変わります。

各inner frameをC6へ入力するときは、通常のC6 header（fragment総数、0始まりindex、
全body byte数）とouter fragment XORを付けます。したがって、長いデータも最終的には
`FFF1`へC6 frameとして順番に送ります。

送信は通常`FFF1`へ行い、outer fragmentは順番に送ります。BLE write type、再送、認証中の
待ち合わせはクライアント実装に依存するため、このwire形式とは分けて扱います。

## コマンド一覧

表のbodyは、特記しない限りそのままC6へ入れ、C6 frame末尾のfragment XORを付けます。
`body checksum`と記載したものは、bodyへ先にchecksumを追加してからC6へ入れます。

## 受信フレーム

### 先頭byteによる入口

受信処理はUUIDだけでなく先頭byteも使います。

| 先頭byte | 条件 | 処理 |
| --- | --- | --- |
| `C1` | 長さ2 byte以上 | device-code認証の次段へ |
| `C3` | hexに`C301000100`を含む | 認証成功 |
| `C6` | 長さ2 byte以上 | C6 frameを再構成して下位packetへ |
| `CF` | 16 byte、`byte[2]==0` | real-time測定 |
| その他 | - | 既知入口では処理なし |

`C1`、`C3`の認証処理とAESのwire上の扱いは[共通認証と暗号化](authentication.md)を参照してください。
ここでいう`C6`はframeの再構成であり、C6 payloadをAES復号する処理ではありません。
受信characteristicのUUIDだけを認証判定に使う仕様ではありません。

### C6再構成後の制御応答

| 先頭byte | 条件 | 意味または処理 |
| --- | --- | --- |
| `CF` | `byte[2]==1` | history record |
| `F2` | `byte[2]==3` / `1` | history完了 / history削除完了 |
| `F1` | len4かつ`byte[3]==0`; len10かつ`byte[2]==2` | 時刻同期完了 / 時刻応答 |
| `F9` | - | recover後の切断処理 |
| `FA` | `byte[2]` | device mode結果 |
| `FB` | `byte[2]` | heart rate状態結果 |
| `FD` | `byte[2]`が0,52,55-60 | 単位、safe、baby、petの結果 |
| `E2` | len7 | error payload |
| `06` | `byte[2]`が0,1,2 | Wi-Fi設定結果 |
| `0A` / `0B` | len3 | Wi-Fi名/password更新ACK |
| `F8` / `F7` / `F6` | `byte[2]`が0,1 | code/certificate/finish結果 |
| `0E` | len3 | network接続結果 |
| `F4` | `byte[2]` | Wi-Fi削除結果 |
| `F5` | `byte[2]` | Wi-Fi設定照会結果 |
| `07` | - | Wi-Fi list fragment |
| `08` / `09` | - | 処理なし |
| `E0` / `E1` | len3 | OTA開始 / OTA成功結果 |
| `E3` | len3 | device state |
| `E4` | len3 | Wi-Fi RSSI |
| `0F` | len3、`byte[2]==0` | bind/unbind状態 |
| `B0` | len3、`byte[2]==2` | token expired |
| `B1` | len3、`byte[2]==0` | token更新準備完了 |
| `11` | `byte[2]` | reset状態 |

`FA`など同じprefixを複数用途で使うbodyは、送受信のsequenceを合わせて解釈します。
safe mode closeの送信bodyは`FD 0A 3F ...`ですが、受信側のFD分岐には`byte[2]==55`
（wire byte `0x37`）などがあり、`0x3F`分岐は確認できません。この送受信の差は未確認
事項として扱い、別機種の定数や別prefixへ補正しません。

### 時刻取得応答

再構成後のF1応答が10 bytes、byte 2が02の場合、次の配置です。
時刻同期の送信で使う年BE16に対し、この受信処理では年をLE16で読みます。
この送受信の差は実機未確認です。

| byte | 内容 |
| --- | --- |
| 0 | F1 |
| 1 | 未解読 |
| 2 | 02 |
| 3..4 | 年、LE16 |
| 5..9 | 月、日、時、分、秒 |

## 測定データ

real-time入口は、先頭が`CF`、長さ16 byte、`byte[2]==0`です。オフセットは0始まりです。

| byte | 読み方 |
| --- | --- |
| `0` | type `CF` |
| `1`, `3` | 未解読 |
| `2` | 00、live測定の識別 |
| `4..5` | 通常測定ではimpedanceのLE16欄。心拍完了ではbyte 4が心拍数 |
| `5` bit7..6 | 11=心拍完了、10=心拍開始、0x=通常測定 |
| `6..7` | weight raw LE16。kgは`raw / 100` |
| `8..10` | encrypted impedanceのLE24欄。物理量への変換は未解読 |
| `11` | unit byte |
| `12` | status: `0` stable、`1` dynamic、`2` overweight、`4` baby/pet stable |
| `13..15` | 未解読、parser未参照 |

status `1`はdynamic weight、`2`はoverweight通知、`4`はbaby/pet stableです。
status `2`をheart停止と解釈してはいけません。status `0`では通常、次のフィールド列を
出力します。

```text
weight_raw, encrypted_impedance_LE24, impedance_LE16, unit_field
```

`byte[5]`のbit7とbit6がともに1ならheart測定完了、bit7だけ1ならheart測定開始です。
心拍完了では`byte[4]`を心拍数として読みます。心拍開始/完了は通常のbody-fat結果とは
別に扱い、同じstatus 0から二重に測定結果を作りません。
この入口はlength16以外のlength・checksum検証を行いません。

## 履歴データ

C6再構成後の`CF`で`byte[2]==1`のrecordは、次のoffsetを読みます。

| byte | 読み方 |
| --- | --- |
| `0` | CF |
| `1`, `3` | 未解読 |
| `2` | 01、履歴の識別 |
| `4..5` | impedanceのLE16欄 |
| `6..7` | weight raw LE16。kgは`raw / 100` |
| `8..10` | impedance候補 LE24。`byte[8]`の上位nibbleはmode引数にも使われる |
| `11` | 未参照 |
| `14..15` | year BE16 |
| `16..20` | month, day, hour, minute, second |
| `12..13`, `21..` | 未参照 |

年月日時分秒はUTCとして解釈する処理になっています。少なくとも21 bytesが必要ですが、
完全なframe長と末尾の意味は未確認です。byte 8上位nibbleをmodeにも使用する読み方は
encrypted impedanceと重なるため、独立したmode欄の位置は未確定です。

## その他の機能

### Wi-Fi一覧

`07` packetを再構成した後のbyte配置は次のとおりです。

| byte | 内容 |
| --- | --- |
| 0 | 07 |
| 1 | 長さ欄候補、受信処理では未参照 |
| 2 | fragment総数 |
| 3 | fragment番号、0始まり |
| 4..5 | 全体長欄候補、受信処理では未参照 |
| 6..末尾直前 | fragment payload |
| 末尾 | XOR欄候補、受信処理では検証しない |

payloadをfragment順に連結し、最後のfragmentで0 byte区切りのrecord列として扱います。
recordは次の構成です。

```text
signal magnitude(1 byte) | BSSID(17 bytes) | Wi-Fi name(variable)
```

signal magnitudeは負値へ変換され、BSSIDとWi-Fi名はhex bytesをUTF-8 decodeします。空名を除外し、
同名を重複除去します。recordの予約値、BSSIDの正規表現、fragment headerの全意味は
未解読です。

## 通信例と検算

履歴要求の完成C6 frameの合成例です。

```text
C6 01 00 03 F2 01 00 37
```

内側bodyはF2 01 00の3 bytesで、内側checksumはありません。最後の37は外側frameのXORです。
単位設定と複数fragmentの検算例は[共通認証と分割形式](authentication.md#固定入力による検算例)にあります。

## 未確認事項

- T9149がT9148と同一のGATT、認証、status、history形式を返すかは未確認です。
- `FFF2`は追加通知候補ですが、受信parserのUUID条件だけから通知の意味を固定できません。
- real-time/history parserは全fieldの予約値、checksum、異常長を検証しません。
- `data[8..10]`の物理量、heart flagの未使用bit、`data[13..15]`、historyの補助fieldは
  wire上に存在しても意味未解読です。
- 同じprefixを複数commandで使うため、単一packetだけで用途を断定できません。
- この資料のframe/checksum/測定値は合成例またはparserの読み方であり、T9148/T9149の
  実機通信を確認した値ではありません。
