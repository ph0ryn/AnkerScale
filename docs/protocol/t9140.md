# T9140 V1 / V2 / V3

[全体索引・確認状況](../protocol.md)

## 対象と確認状況

T9140系は、`AC 02`で始まるフレームを使うBLEプロファイルです。V1、V2、V3は
サービスとcharacteristicのUUIDが異なりますが、確認できた送受信フレームの構造は
共通です。以下はクライアント実装から確認できた通信形式であり、すべての実機や
firmwareでの相互接続を保証するものではありません。

`eufy T9140_V1`などのV1/V2/V3はクライアント内のvariant名です。実機の型番との
対応、広告フラグとvariantの対応、通知の分割条件は実機での確認が必要です。

## 検出とGATT

| variant | service | notify | write |
| --- | --- | --- | --- |
| V1 | `0000ffb0-0000-1000-8000-00805f9b34fb` | `0000ffb2-0000-1000-8000-00805f9b34fb` | `0000ffb1-0000-1000-8000-00805f9b34fb` |
| V2 | `4143f6b0-5300-4900-4700-414943415245` | `4143f6b2-5300-4900-4700-414943415245` | `4143f6b1-5300-4900-4700-414943415245` |
| V3 | `4143f7b0-5300-4900-4700-414943415245` | `4143f7b2-5300-4900-4700-414943415245` | `4143f7b1-5300-4900-4700-414943415245` |

同じ `eufy T9140` というlocal nameから、広告に含まれるvariant情報を使ってV1/V2/V3
を選ぶ実装があります。variantを判定できない場合に、いずれかの初期化を自動で
送ることはできません。

広告のvariant候補を同じ位置で判定する場合は、AD構造を次のように扱います。
`ad[0]`はlength、`ad[1]`はAD typeで、`ad[1] = 0x03`のフィールドについて
`ad[4..5]`の2 byteを比較します。比較されるバイト列はV1が`B0 FF`、V2が`B0 F6`、
V3が`B0 F7`です。これはアプリ内の候補選択条件であり、実機型番の証明ではありません。

## 接続と初期化

### 送信方式と要求順

確認できたクライアントは、単位・時刻・履歴要求を通知のプロトコル応答を待たずに
送ります。測定完了ACKはコマンドとして定義されていますが、通常の測定フローから
送られることは確認できていません。

V1/V2の接続後手順は次の順です。時刻は接続完了通知を基準にしたクライアント側の
予約時刻で、機器が要求する待ち時間を意味しません。

| 接続完了から | コマンド | 用途 |
| --- | --- | --- |
| 200 ms | 時刻同期 | Unix秒を設定 |
| 600 ms | 単位設定 | 保存済み単位を設定 |
| 1000 ms | 履歴要求 | 保存履歴を要求 |

V3は、最初に時刻取得を行います。

| 接続完了から | コマンド | 用途 |
| --- | --- | --- |
| 200 ms | 単位設定 | 保存済み単位を設定 |
| 600 ms | 時刻取得 | scale側の時刻を取得 |

V3の時刻取得応答を受けると、単位設定を行い、400 ms後に時刻同期、800 ms後
に履歴要求を送ります。ここでの400 msと800 msは、時刻取得応答を受けてこの後続処理を
開始した時点からの予約時刻です。時刻取得のread timeoutでは、時刻取得を再送する
処理があります。

### GATT write・MTU・認証

V1/V2/V3を扱う確認済みの送信経路は、GATTの応答ありwriteを使います。
旧版にはWrite Without Responseを使う経路もあります。機器からの制御結果や測定結果は、
別途notify characteristicで受け取ります。
MTU拡張要求は行いません。接続後の認証コールバックは空で、T9140固有の認証フレームは
確認できていません。

## 送信フレーム

### checksum

送信フレームはテンプレートを組み立てた後、先頭の `AC 02` を除いたデータ部の
byte和の下位8 bitを末尾に付加します。

```text
SUM8 = (frame[2] + frame[3] + ... + frame[last]) & 0xff
```

テンプレート末尾の `CC` または `CF` もデータ部なので、checksumの計算に含みます。
`AC 02` は含みません。受信フレームの末尾については、後述のパーサーはchecksumを
検証していません。

## コマンド一覧

### 固定コマンド

表の完成フレームは、checksumを含む送信列です。

| 用途 | 完成フレーム | 使用variant・備考 |
| --- | --- | --- |
| 時刻取得 | `AC 02 F3 00 00 00 CC BF` | V3の通常手順で使用 |
| 時刻同期 | `AC 02 F2 t0 t1 t2 t3 CC ss` | `t0..t3`はUnix秒のLE32、`ss`はSUM8 |
| 単位取得 | `AC 02 FE 1B FF 00 CC E4` | 明示的に要求した場合の応答取得 |
| 単位設定・kg | `AC 02 FE 06 00 00 CC D0` | unit code `0` |
| 単位設定・lb | `AC 02 FE 06 01 00 CC D1` | unit code `1` |
| 単位設定・st | `AC 02 FE 06 02 00 CC D2` | unit code `2` |
| 測定完了ACK | `AC 02 FE 1D 00 00 CC E7` | 送信メソッドはあるが、通常手順での使用は未確認 |
| 履歴要求 | `AC 02 FF 00 00 00 CF CE` | すべてのvariantの通常手順で使用 |

時刻同期の `t0..t3` は、Unix秒を下位byteから並べます。たとえば
`0x12345678`なら次のフレームです。

```text
AC 02 F2 78 56 34 12 CC D2
```

`AC 02 F2 00 00 00 00 CC BE`は、時刻が0のときの例です。時刻byteの合計が
256の倍数になる別の時刻でもchecksumは`BE`になり得ます。現在時刻では通常、
checksumも変化します。

## 受信フレーム

受信側は、確認できた範囲では最終byteをchecksumとして再計算しません。`x`はその
分岐で参照されないbyteです。`x`をchecksumや固定値とみなして受信条件を追加する
ことはできません。

### 8 byteの状態・測定通知

基本形は `AC 02` から始まる8 byteです。体重rawは `byte[2..3]` のunsigned BE16
で、アプリでは `raw / 10` をkg相当として扱います。これはアプリの解釈であり、
単位設定後の機器内部スケールを独立に証明するものではありません。

| 形式 | 解釈 |
| --- | --- |
| `AC 02 ww_hi ww_lo x x CE x` | 動的体重。`raw = ww_hi << 8 \| ww_lo` |
| `AC 02 ww_hi ww_lo x x CA x` | 安定体重。`raw = ww_hi << 8 \| ww_lo` |
| `AC 02 FD 00 00 00 CB x` | インピーダンス測定開始 |
| `AC 02 FD 01 rr_hi rr_lo CB x` | インピーダンス結果。rawはunsigned BE16 |
| `AC 02 FE 10 x x CC x` | 測定データ送信完了 |
| `AC 02 FE 03 x x CC x` | 過荷重 |
| `AC 02 FE 00/01/02 x x CF x` | 履歴なし、履歴開始、履歴終了 |
| `AC 02 FE 1A x x CC x` | 電源オフ |
| `AC 02 FE 1C FF x CC x` | 電源オフ準備 |

状態通知で参照されないbyteの意味、受信checksumの位置と有効性は未確認です。

### 制御応答

次の制御応答が確認されています。`x`は参照されないbyteです。

| 形式 | 解釈 |
| --- | --- |
| `AC 02 FE 06 FE x CC x` | 単位設定成功 |
| `AC 02 FE 06 FF x CC x` | 単位設定失敗 |
| `AC 02 FE 07 x x CC x` | 時刻同期成功 |
| `AC 02 FE 08 x x CC x` | 時刻同期失敗 |
| `AC 02 FE 1B unit x CC x` | 単位取得結果。`unit`は単位code |

### 9 byteの測定時刻通知

標準的な形は次の9 byteです。

```text
AC 02 F1 t0 t1 t2 t3 CC x
```

`t0..t3`は測定時刻のunsigned LE32です。末尾byteは確認されません。確認した
パーサーは長さを9 byteに固定せず、最低8 byteの入力で `byte[2]=F1` と `byte[7]=CC`
を満たす場合にも同じ位置を読みます。そのため、wire上の正しい最小長を8 byteと
みなすことはできません。

### 16 byte・17 byteの結合通知

V1/V2/V3の新しいパーサーには、複数通知を結合した入力を分割する処理があります。

- 16 byteは、`byte[8..15]`を8 byteとして先に処理し、その後`byte[0..7]`を処理します。
  受信列の順序とは逆です。
- 17 byteは、`byte[9..16]`の8 byteを9 byte配列の先頭へコピーし、残りの1 byteを
  `0`のまま処理します。その後、`byte[0..8]`の9 byteを処理します。

17 byteの後半を0で埋めた9 byteが、実際の無線上の9 byte通知を意味するかは不明です。
分割が発生する条件、逆順処理が機器側の送信順序を表すかも未確認です。

### 19 byteの履歴・リアルタイム通知

`AC 02`で始まる19 byte通知は、`byte[2]`によって解釈が分かれます。

`byte[2]`が `FE` 以外の場合は、2件の履歴recordです。

| record | timestamp | weight | impedance |
| --- | --- | --- | --- |
| 1 | `byte[3..6]`、unsigned LE32 | `byte[7..8]`、unsigned BE16 | `byte[9..10]`、unsigned BE16 |
| 2 | `byte[11..14]`、unsigned LE32 | `byte[15..16]`、unsigned BE16 | `byte[17..18]`、unsigned BE16 |

timestampが0、またはweightが0以下の場合、そのrecordはアプリから送られません。
この形式では `byte[9..10]` はrecord 1のインピーダンスです。T9146系の18 byte
履歴で参照されない `byte[9..10]` とは別の形式です。

`byte[2]`が `FE`の場合は、先頭recordだけをリアルタイム測定として扱います。
timestamp、weight、impedanceの位置は上表のrecord 1と同じで、`byte[11..18]`は
このパーサーでは無視されます。

### 測定の組み合わせ

通常の体組成測定では、次のような通知が別々に届きます。

1. `CE`または`CA`で体重を更新する。
2. `FD 00 CB`でインピーダンス測定開始を受ける。
3. `FD 01 rr_hi rr_lo CB`でインピーダンスを受ける。
4. `F1`通知で測定時刻を受ける。
5. `FE 10 CC`で測定完了を受ける。

アプリは測定完了時点で保持している体重、インピーダンス、測定時刻を1件の結果に
組み合わせます。実機が常にこの順序で通知すること、各通知が必ず1回だけ届くことは
未確認です。

### V3のGET_TIME応答

V3の時刻取得応答は、少なくとも次の位置に2つのUnix時刻を含みます。

```text
AC 02 F3 t1_0 t1_1 t1_2 t1_3 t2_0 t2_1 t2_2 t2_3
```

`t1`と`t2`はそれぞれunsigned LE32です。パーサーの共通入口は8 byte以上しか
要求しませんが、実際には`byte[10]`まで読むため、11 byte未満のF3入力を安全に
処理できません。応答の末尾byte、時刻の意味、wire上の最小長は未確認です。

## 測定データ

### 個別通知による測定

体重の安定と、測定全体の完了は別の通知です。

1. CE通知で変動中の体重を受信します。
2. CA通知で安定した体重を得ます。この時点では体組成測定が完了したとは限りません。
3. FD 00 / FD 01でインピーダンス測定の開始・結果を受信します。
4. F1で測定時刻を受信する経路があります。
5. FE 10で測定データ送信完了となり、保持した体重・インピーダンス・時刻を1件として扱います。

上記は各通知を組み合わせる流れです。すべての機種が毎回この順序・全通知を送ると
実測したものではありません。19-byteのFE形式は、時刻・体重・インピーダンスを
1つの通知に含む別経路です。両方の経路で同じ測定が届く可能性は実機未確認です。

## 履歴データ

### 履歴

履歴要求後は、FE 01 / CFが開始、19-byte recordがデータ、FE 02 / CFが終了を示します。
FE 00 / CFは履歴なしです。19-byte形式の体重もraw / 10 kgとして解釈します。
このファミリーでは、本資料の確認済みコマンドに独立した履歴削除要求はありません。
測定完了ACKの要否と送信タイミングは未確認なので、履歴要求や履歴終了とは区別します。

## その他の機能

### 旧版との違い

旧版クライアントで確認できるT9140はFFB0系のV1相当UUIDだけです。V2/V3のUUIDや
variant名は確認できません。送信側は同じ `AC 02` とSUM8を使い、履歴要求、単位設定、
時刻同期を行います。

受信側の差は次の通りです。

| 項目 | 旧版 | V1/V2/V3の新しいパーサー |
| --- | --- | --- |
| 接続後の初回要求 | 通知購読開始後、約300 msで履歴要求 | variantごとの接続後手順 |
| 履歴後の要求 | 履歴なし・履歴終了後に時刻同期、成功後に単位設定 | V1/V2は時刻同期→単位→履歴、V3は時刻取得から開始 |
| 受信長 | 19、9、8 byte | 19、16/17の分割、9、8、V3のF3 |
| 19 byteのFE | 常に2件の履歴として処理 | 先頭recordだけをリアルタイムとして処理 |
| V2/V3 UUID | なし | あり |

旧版の19 byte parserは `AC 02` の先頭や `byte[2]=FE` を確認せず、長さだけで2件の
履歴として処理します。旧版の9 byte parserも、長さ9、`byte[2]=F1`、`byte[7]=CC`
以外の末尾byteや `AC 02` を検証しません。

## 通信例と検算

時刻同期でUnix秒を0x12345678に固定した送信例です。

```text
AC 02 F2 78 56 34 12 CC D2
```

先頭AC 02を除いたbyte和の下位8 bitはD2です。固定コマンドの完成列はコマンド一覧にあります。
この例は実機キャプチャではなく検算用です。

## 未確認事項

- V1/V2/V3のvariant名・広告情報と実機型番の対応。
- 実機がV1/V2/V3で同一の通知形式を返すか、variant固有のwire差があるか。
- 16/17 byte通知が発生する条件、通知結合の境界、17 byteの0 paddingの意味。
- 受信checksumの存在、種別、対象範囲、検証要否。不正checksumを機器がどう扱うか。
- 19 byteのFE形式で無視される`byte[11..18]`の意味。
- F3応答のt1/t2の時計の意味、応答の末尾と長さ、再送条件。
- 測定完了ACKが必要になるvariantと送信タイミング、ACK応答の形式。
- unit code変更が実機の表示やweight rawのスケールに与える影響。
- 認証フレームを必要とする実機や、未確認の接続・切断条件。
