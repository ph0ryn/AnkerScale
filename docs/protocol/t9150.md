# T9150 / T9130

[全体索引・確認状況](../protocol.md)

## 対象と確認状況

T9150/T9130系は、`FFF0` serviceの中で制御、認証・分割データ、real-time測定を
別characteristicへ分けるBLE体重計プロファイルです。ここではGATT、MTU、送受信byte列、
ユーザー・履歴・Wi-Fi・token・logの形式を記載します。

T9130はT9150と同じプロファイル候補として扱われていますが、T9130の実機で全ての
packetが同じことは確認できていません。本資料は固定版アプリの通信処理から復元した
仕様であり、メーカー仕様書でも、T9150/T9130の実機キャプチャでもありません。
認証・AES・C1/C2/C3の交換は[共通認証と暗号化](authentication.md)へ分離しています。

## 検出とGATT

| 役割 | UUID | 使い方 |
| --- | --- | --- |
| service | `0000FFF0-0000-1000-8000-00805F9B34FB` | 主service |
| primary notify / control write | `0000FFF1-0000-1000-8000-00805F9B34FB` | 通知購読、制御write |
| auth/data notify + write | `0000FFF2-0000-1000-8000-00805F9B34FB` | 認証、分割データ、DFU ACK |
| real-data notify | `0000FFF3-0000-1000-8000-00805F9B34FB` | real-time測定専用 |
| device information service | `0000180A-0000-1000-8000-00805F9B34FB` | firmware revision read |
| firmware revision | `00002A26-0000-1000-8000-00805F9B34FB` | version値 |
| battery service | `0000180F-0000-1000-8000-00805F9B34FB` | battery read |
| battery level | `00002A19-0000-1000-8000-00805F9B34FB` | battery値 |

## 接続と初期化

接続後の基本順序は次の通りです。

1. `FFF0` serviceをdiscoverする。
2. `FFF1`をnotifyとして有効化し、`FFF2`を通常writeへ設定する。
3. `FFF1`をcontrol writeとして保存する。
4. `FFF1`のCCCD書き込み成功後、`FFF3`をnotifyとして有効化する。
5. `FFF3`のCCCD書き込み成功後、`FFF2`をnotifyとして有効化する。
6. `FFF2`のCCCD書き込み成功後、認証を開始する。

T9150系は接続時にATT MTU 244を要求します。device側からcontrol response `02`で分割用の
アプリ値`M`を受け取った場合、`M`が20より大きければ以後の分割単位へ反映します。初期の
`M`は20です。`M`はATT MTUとは別の転送単位であり、ATT MTUから自動計算する値ではありません。
ATT MTU交換が完了しても、3つのCCCD購読と認証が完了したとは限りません。

### 認証後の初期化例

登録済み機器への接続で確認した送信予約の例です。認証成功からの相対時刻であり、
すべてが測定値取得に必須という意味ではありません。設定値と接続状態によって一部を省略します。

| 認証成功から | FFF1のコマンド | 条件・補足 |
| --- | --- | --- |
| 200 ms | 転送サイズ取得 02 00 | 分割単位Mを取得 |
| 400 ms | 単位設定 | 保存済み設定 |
| 600 ms | 時刻同期 | UTC epoch秒 |
| 800 ms | safe mode設定 | 保存済み設定 |
| 1000 ms | 心拍open/close | 保存済み設定 |
| 1200 ms | token状態取得 | 接続設定による |
| 1400 ms | Wi-Fi MAC取得 | 27 00 |
| 1600 ms | data review設定 | 強制更新処理中は省略 |
| 1800 ms | trend設定 | 強制更新処理中は省略 |
| 2200 ms | bind状態取得 | 接続設定による |
| 2400 ms | tap-to-change設定 | 保存済み設定 |

これと並行してfirmware/battery等をreadし、認証成功から2000 ms後にユーザー情報の
同期を開始する経路があります。強制更新中や既に同期中の場合は省略します。
ユーザー同期・履歴はFFF2の開始要求、応答、分割payload、終了要求を使う別のsequenceです。

## 送信フレーム

- `FFF1`へ送る制御bodyは、制御・OTA・RSSI・token状態などです。
- `FFF2`へ送るbodyは、認証、設定payload、ユーザー、履歴、token本体、logです。
- `FFF3`へのwriteはありません。real-time通知専用です。
- 通常のbodyにはT9148系のC6 checksumはありません。bodyはBLE writeへ直接送ります。
- 長いpayloadは`00 | fragment_index | payload`で転送単位Mに従って分割します。

### データ分割

hex文字列は1 fragmentあたり`M - 2` byteへ分け、各fragmentの先頭へ2 byteを付けます。

```text
00 | fragment_index | payload
```

`M`が20ならpayload上限は18 byteです。hex payload `AA BB CC`の先頭fragmentは
`00 00 AA BB CC`です。checksumは付加されません。

受信側は先頭2 bytesの`00 index`を取り除き、残りのpayloadを連結します。
データ種別と終了は別の制御応答で区別します。総fragment数やchecksumはこのheaderに
含まれません。複数の転送種別を同時に混ぜた場合の復元方法は未確認です。

### 設定・token・log・7日履歴・FFF2

| 機能 | wire bodyまたはprefix | payload |
| --- | --- | --- |
| Wi-Fi設定開始 | `03 01 01` | なし |
| Wi-Fiデータ準備 | `03 04 02 step lengthLE16` | step 0では文字列hex+`00`の長さ |
| Wi-Fiデータ送信 | `00 index` + 文字列hex+`00` | MTU分割 |
| Wi-Fiデータ終了 | `03 01 03` | なし |
| Wi-Fi設定完了 | `03 01 04` | なし |
| Wi-Fi list開始/終了 | `04 01 01` / `04 01 02` | なし |
| Wi-Fi設定cancel | `03 01 05` | なし |
| token送信開始 | `09 03 01 lengthLE16` | token payloadの長さ |
| token送信終了 | `09 01 02` | なし |
| log取得開始 | `01 01 01` | なし |
| log取得 | `01 09 02 logLength[4] logStart[4]` | hex文字列から各4 byteを設定 |
| log送信終了 | `01 01 03` | なし |
| 7日履歴送信開始 | `0A 03 01 lengthLE16` | record長 |
| 7日履歴送信終了 | `0A 01 02` | なし |

log開始応答は先頭01、byte 2=01で、byte 3..6がlog length、7..10がstart addressです。
取得要求ではこの2つの4-byte列をそのまま同じ順序で返します。
蓄積logはUTF-8でdecodeし、先頭01、byte 2=03の通知で終了します。

### ユーザー・履歴の送信手順・FFF2

| 機能 | 開始 | 終了 |
| --- | --- | --- |
| 全ユーザー情報 | `05 03 01 53 00` | `05 01 02` |
| user name | `08 03 01 6C 02` | `08 01 02` |
| online user | `05 03 06 38 00` | `05 01 07` |
| device-selected user | `05 02 08 00` | `05 03 08 01 00` |
| user削除 | `05 03 03 38 00` | `05 01 04` |
| user query | `05 02 05 00` | `05 02 05 01` |
| history user ID | `02 03 07 28 00` | `02 01 08` |
| history本体 | `02 01 09` | `02 02 0A 00` |

#### ユーザー情報本体

`全ユーザー情報`のpayloadは次の順序です。先頭の各fragmentには`00 index`が付きます。

```text
user_id(80 hex chars)
member_id(32 hex chars)
userInfoUpdateTime(LE32)
age(1) | sex(1) | height(LE16) | level(1) | weight(LE16)
imgIndex(1) | nameUpdateTime(LE32) | goalPlan(1) | goalUpdateTime(LE32)
goalWeight(LE16) | goalBodyFat(LE16) | goalMuscleMass(LE16)
```

user name payloadはhyphenを除いたmember IDと、bitmap化したnameを1208 hex文字へ0埋め
したものです。T9130ではnameを最大4文字へ切り詰めます。

online userとuser削除のpayloadは`user_id(80 hex chars) + member_id(32 hex chars)`です。
history user IDは通常のuser ID、guest時は全zero文字列を送ります。

#### token payload

token送信は次の順序です。

```text
expires_in(LE32) |
access_token_length_plus_1 | access_token | 00 |
refresh_token_length_plus_1 | refresh_token | 00
```

末尾の`00`を含めてlengthを計算します。length plus 1を通常の文字列長へ置き換えては
いけません。

## 受信フレーム

| UUID/先頭 | 処理 |
| --- | --- |
| FFF2 + `0x0B` | DFU ACK |
| FFF2 + `C1` | 認証次段 |
| FFF2 + `C3` | `C301000100`を含むと認証成功 |
| FFF2 + その他 | new-data sequence |
| FFF1 | control response |
| FFF3 | real-time測定 |

### FFF1 control response

| 先頭byte | 条件 | 処理 |
| --- | --- | --- |
| `0F` | len3、`data[2]=0/1` | OTA開始結果 |
| `1B` | len>3、`data[2]=0`またはその他 | OTA成功/失敗 |
| `1A` | len3 | device state。`data[2]=1`を成功扱い |
| `19` | len>4、`data[2]==0` | `data[3]` RSSI |
| `27` | len8 | bytes2..7をMACへ変換 |
| `23` | len3、`data[2]==2` | token expired |
| `02` | len4 | bytes2..3 LE16をMTUへ反映 |
| `21` | len4、`data[3]==0` | data review ACK |
| `22` | len>3 | trend ACK |
| `0E` | len>3、`data[3]==0` | bind状態 |
| `47` | `data[2]` | reset状態 |

### FFF2 new-data response

| `data[0]` | 追加条件 | 処理 |
| --- | --- | --- |
| `0` | - | fragment headerを除去してpayload連結 |
| `1` | `data[2]`が1/3 | log開始/終了 |
| `2` | `data[2]`が7/8/10 | history user ID、history取得、history終了ACK |
| `3` | `data[2]`が1-4 | Wi-Fi設定sequence ACK |
| `4` | `data[2]==2` | Wi-Fi listをflush |
| `5` | `data[2]`が1-8 | user sequence ACK |
| `8` | `data[2]==1/2`、`data[3]==0` | user nameまたは次のuserへ進む |
| `9` | `data[2]==1`、`data[3]==0` | token payload送信許可 |
| `10` | `data[2]==1/2` | 7日履歴送信/完了 |

### 受信ユーザー一覧

再構成したpayloadは、40-byte user ID、1-byte member count、count件の24-byte recordです。
複数のuser IDの一覧を続けて受信する経路もあります。各recordの構成は次の通りです。

```text
member_id(16 bytes) | update_time(LE32) | unreferenced(4 bytes)
```

末尾4 byteは受信parserが参照しません。送信用の83-byteユーザー情報とは別の形式です。

## 測定データ

FFF3の通知は先頭byteで測定状態を分けます。

| `data[0]` | 処理 |
| --- | --- |
| `0x01` | weight parser |
| `0x02` | bytes4..7からencrypted impedanceをLE32で保存 |
| `0x06`かつ`data[2]==1` | device-selected user終了後のuser処理 |
| その他 | 未処理 |

`0x02`の値は次のweight packetへ持ち越されます。

### weight packet

`data[0]==0x01`の配置は次の通りです。offsetは0始まりです。

| byte | 読み方 |
| --- | --- |
| `2` | status: `1`/`13` dynamic、`101` heart開始、`5` stable weight |
| `3` | 成人stable判定`0x80`/`0xC0`、`0x40`は未完了終了 |
| `4..5` | weight raw LE16。kgは`raw / 100` |
| `7` | heart rate。`0xFF`は0 |
| `10..11` | 成人stable時の第3フィールド。LE16のplain impedance slot |
| `6`, `8..9`, `12..` | 未解読または未参照 |

成人stableの出力列は次の形です。

```text
weight_raw, encrypted_impedance, data[10..11]LE16, 0, heart_rate
```

`data[10..11]`は、別に届くtype `0x02`のencrypted impedanceと同一とは限りません。
心拍数は`data[7]`です。baby/pet状態では同じweightを別のstable扱いにします。

parserの判定順は次の通りです。上の条件に一致した時点で、そのpacketの処理を決めます。

1. `data[3]`が`0x80`または`0xC0`なら成人の完了として扱い、保留していたtype `0x02`
   のencrypted impedanceを出力してから消去します。
2. 通常測定モードで`data[2] == 5`ならstable weightとして扱います。
3. `data[3] == 0x40`ならshutdownとして扱います。
4. `data[2] == 1`または`data[2] == 13`ならdynamic weightとして扱います。
5. `data[2] == 101`ならheart開始として扱います。

心拍開始通知は同じ状態が続く間は重複を抑え、type 01のbyte 2が101以外になると解除します。

real-time parserは最低長、checksum、未使用byteを検証しません。上表は解析器が読む
offsetであり、firmware全体のwire仕様を保証する定義ではありません。

## 履歴データ

type `2`のhistory payloadは、先頭32 hex文字をmember ID、その後を24 hex文字ずつの
recordとして読みます。

| record hex範囲 | 内容 |
| --- | --- |
| `0..7` | createTime、LE32 |
| `8..11` | weight raw LE16。kgは`raw / 100` |
| `12..13` | heart rate |
| `14..15` | type byte（1 byte）。`01`ならencrypted impedanceを使う |
| `16..23` | type byteが`01`のときだけ読むencrypted impedance、LE32 |

type byteが`01`のrecordだけencrypted impedanceを読み、値が0より大きいとき、アプリ内の
impedance欄へplaceholderの`10.0`、それ以外へ`0.0`を設定します。これはphysical
impedanceの復元値ではありません。
history終了ACKは`data[0]==2`、`data[2]==10`で、`data[3]==1`なら
`02 02 0A 00`を返します。

## その他の機能

### Wi-Fi一覧

type `0` fragmentを連結し、type `4`の`data[2]==2`でflushします。0 byte区切りの
各recordは次の形式です。

```text
signal magnitude(1 byte) | BSSID(17 bytes) | Wi-Fi name(variable)
```

signal magnitudeは負値へ変換され、BSSIDとWi-Fi名はhex bytesをUTF-8 decodeします。空白名を
除外し、同名を重複除去します。headerの予約値、BSSID表現、recordのfirmware保証範囲は
未解読です。

## 通信例と検算

時刻同期でUnix秒を0x12345678に固定した送信例です。FFF1へ次の8 bytesを送ります。

```text
04 06 78 56 34 12 08 01
```

C6包装や追加checksumはありません。分割データの検算例として、転送単位M=20で
3-byte payload AA BB CCを送る場合のFFF2への最初のfragmentは次の5 bytesです。

```text
00 00 AA BB CC
```

先頭00はデータfragment種別、次の00はindexです。これらは実機キャプチャではなく合成例です。

## 未確認事項

- T9130がT9150と同一のGATT、MTU応答、status byte、user/history payloadを返すかは未確認です。
- `FFF1`は通知とcontrol write、`FFF2`は通知とauth/data write、`FFF3`はreal-data通知
  という分担は静的なプロファイル上の役割です。実機のpropertiesは別途確認が必要です。
- real-time/history parserはchecksum、異常長、予約byteを検証しません。
- `data[10..11]`はstable weightの第3フィールド、心拍数は`data[7]`です。type `0x02`
  のencrypted impedanceと混同しないでください。
- T9148系の旧prefixがT9150側の定数として残っていても、T9150の確認済みsequenceへ
  自動的に追加できません。
- 本資料のframe、checksum、数値例は合成例またはparserの読み方であり、T9150/T9130の
  実機通信を確認した値ではありません。
