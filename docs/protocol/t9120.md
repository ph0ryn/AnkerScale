# T9120 / T9146 / T9146 C1 / T9147

[全体索引・確認状況](../protocol.md)

## 対象と確認状況

T9120、T9146、T9146 C1、T9147は基本的なGATT構成と測定形式を共有します。
T9147のsafe modeと起動順序、C1の単位コードには差があります。
全機能がすべての機種で利用できるという意味ではありません。

本文は送受信処理の解析で確認した形式です。実機由来の情報は
[旧実測記録](#旧実測記録)にまとめ、合成例とは区別しています。

## 検出とGATT

local nameとGATT構成を照合します。サービスUUIDが広告に必ず含まれるとは限りません。

対象local nameは `eufy T9120`、`eufy T9146`、`eufy T9146 C1`、`eufy T9147` です。

| 役割 | UUID |
| --- | --- |
| service | `0000fff0-0000-1000-8000-00805f9b34fb` |
| notify | `0000fff4-0000-1000-8000-00805f9b34fb` |
| 同じ先頭byteを待つ | `0000fff1-0000-1000-8000-00805f9b34fb` |

このファミリーの確認した接続手順にはC0〜C3認証がありません。T9120の旧実測記録でも認証は
観測されていません。後継機のFFF0サービスと同一視することはできません。

## 接続と初期化

### 接続から初期化まで

1. GATT接続後にFFF0サービスとFFF4/FFF1を取得します。
2. FFF4の通知を有効にします。
3. FFF1へ単位・時刻・履歴要求を送ります。
4. 測定・履歴・制御応答をFFF4で受信します。

この手順ではMTU拡張を要求しません。下表は確認したクライアントの送信スケジュールです。
時間原点は通知設定を開始した直後で、CCCD書き込み完了とは異なります。
値はコマンド送信の予約時刻であり、実際のGATT writeはさらに100 ms後です。
機器が要求する最小間隔・最大待ち時間としては未確認です。

### T9120 / T9146 / T9146 C1

| 通知設定開始直後から | コマンド | 用途 |
| --- | --- | --- |
| 200 ms | 単位設定 | 表示単位設定 |
| 600 ms | 時刻同期 | ローカル日時同期 |
| 1200 ms | 履歴要求 | 保存履歴要求 |

起動時には保存済みの単位コードを送ります。

### T9147

| 通知設定開始直後から | コマンド | 用途 |
| --- | --- | --- |
| 200 ms | 単位設定 | 表示単位設定 |
| 600 ms | 時刻同期 | ローカル日時同期 |
| 1200 ms | safe mode設定 | アプリ設定に従うsafe mode設定 |
| 1800 ms | 履歴要求 | 保存履歴要求 |
| 2200 ms | 単位設定 | 単位設定の再送 |

### 書き込みと応答

確認した送信方式はGATTの応答ありwriteです。単位・時刻・履歴要求/削除は、
各コマンドに対するプロトコル応答を待たず送信します。
切断要求とdevice情報要求では、送信と同じ先頭byteの通知を応答として待ちます。
確認したクライアントの待ち時間は5秒ですが、これは機器の応答期限を保証しません。
transaction IDによる厳密な対応づけもありません。

旧実測記録には応答なしwriteの記述もありますが、全送信ログを再照合できていません。
これを全T9120系の必須write方式とはしません。

## 送信フレーム

通常コマンドはFFF1へ直接送ります。単位・拡張モードの11-byteフレームは末尾にXORを持ちます。
時刻・履歴要求などの短いコマンドには同じchecksumを追加しません。

## コマンド一覧

### 通常コマンド

下表はchecksumを含めた完成形です。日時コマンドの可変欄を除き、空白を除いた
hexをbyte列に変換したものが送信内容です。

| 用途 | 完成フレーム | プロトコル応答待ち |
| --- | --- | --- |
| 時刻取得 | `f1 00` | なし |
| 時刻同期 | `f1 YH YL MM DD hh mm ss` | なし |
| 単位kg | `fd 00 00 00 00 00 00 00 00 00 fd` | なし |
| 単位lb | `fd 00 01 00 00 00 00 00 00 00 fc` | なし |
| 単位コード2 | `fd 00 02 00 00 00 00 00 00 00 ff` | なし |
| 履歴要求 | `f2 00` | なし |
| 履歴削除 | `f2 01` | なし |
| 切断要求 | `f3 00` | 同じ先頭byteを待つ |
| device情報要求 | `f4 00` | 同じ先頭byteを待つ |

時刻・f2/f3/f4の短いコマンドにchecksum byteは追加されません。
全コマンドに同じchecksum規則を適用することはできません。

### 単位

単位設定は10-byte templateのbyte 2を変更し、全10 bytesのXORを末尾へ加えた
11 bytesです。単位コードはkg=0、lb=1、st=2です。確認した単位変更では、
T9120/T9146/T9147はkg=0、その他=1を送り、T9146 C1ではst=2も使います。
したがってコード2の送信例は、全機種のst対応を示しません。

受信処理は表示単位を参照せず、体重rawを常に100で割ってkgへ変換します。
これはアプリの解釈です。単位切り替え前後の実機rawの比較は未確認です。

### 日時

| byte | 内容 | 形式 |
| --- | --- | --- |
| 0 | コマンド | f1 |
| 1..2 | 西暦 | BE16 |
| 3 | 月 | 1〜12 |
| 4 | 日 | 暦日 |
| 5 | 時 | 0〜23 |
| 6 | 分 | 0〜59 |
| 7 | 秒 | 0〜59 |

端末のローカル日時を送ります。UTC epochではなく、タイムゾーンやUTC offset、
長さのフィールドもありません。

合成例: 2026-06-20 23:51:20。

```text
f1 07 ea 06 14 17 33 14
```

### 拡張モード

下表の定数はすでにchecksumを含む11 bytesです。

| 機能 | 完成フレーム | 確認した範囲 |
| --- | --- | --- |
| safe modeを開く | `fd 38 03 00 00 00 00 00 00 00 c6` | T9147の通常初期化で使用 |
| safe modeを閉じる | `fd 37 03 00 00 00 00 00 00 00 c9` | T9147の通常初期化で使用 |
| OTA mode | `fd 39 03 00 00 00 00 00 00 00 c7` | 開始コマンドのみ。更新転送は未解読 |
| 抱きかかえ測定に入る | `fd 3b 03 00 00 00 00 00 00 00 c5` | 送信形式を確認。機種別対応は未確認 |
| 抱きかかえ測定を出る | `fd 3c 03 00 00 00 00 00 00 00 c2` | 同上 |
| ペット測定に入る | `fd 3d 03 00 00 00 00 00 00 00 c3` | 同上 |
| ペット測定を出る | `fd 3e 03 00 00 00 00 00 00 00 c0` | 同上 |

抱きかかえ/ペットの開始・終了では、クライアント側も測定モードを切り替えます。
各T9120系製品のファームウェアが対応するかは未確認です。

## 受信フレーム

受信処理はUUIDを使って分岐せず、長さと内容で処理します。最初に2 bytes未満を
無視し、次に7/14-byteを時刻系として処理します。その後で先頭byteを調べます。
この優先順から、長さだけで時刻と認定するアプリ挙動があり、任意の7-byteデータを
有効な時刻と保証するものではありません。

| 条件 | アプリの解釈・制約 |
| --- | --- |
| 長さ7 | 旧形式の時刻取得イベント。値自体はここで解読しない |
| 長さ14 | 7-byte暦日時を2つとして時刻イベントを発行 |
| 先頭f1、長さ8以外、byte 1=0 | 時刻同期成功 |
| 先頭f1、長さ8 | 無視する |
| 先頭f2、byte 1=0 | 履歴同期成功/完了イベント |
| 先頭f2、byte 1=1 | 履歴削除成功イベント |
| 先頭f3 | 切断関連イベント。byte 1の値は検査しない |
| 先頭f4 | この受信処理では解読しない |
| 先頭f5 | 単位同期応答。詳細payloadは検査しない |
| 先頭fd、byte 1=0x37/0x38/0x39 | safe mode閉/開、OTA modeイベント |
| 先頭cf、長さ11 | live測定 |
| 先頭cf、長さ18 | 履歴測定 |

このため`f3 00`を、必ず直前のクライアント切断要求に対するACKとは断定できません。
またf2 00は受信時に履歴同期完了として処理されますが、実機の履歴送出順序と
完了保証については完全なキャプチャがありません。

14-byte時刻データはヘッダーなしで、`0..1`年BE16、`2`月、`3`日、`4`時、`5`分、
`6`秒を1組とし、同配置を`7..13`に繰り返します。7-byte旧形式の暦配置や、
2日時それぞれの機器内の正確な意味は、長さの対応だけで確定しません。

## 測定データ

取得した体重・インピーダンスからの体脂肪率などの計算は、
[体組成の計算](bodyComposition.md)にまとめています。

| byte | 内容 | 解釈 |
| --- | --- | --- |
| 0 | type | cf |
| 1..2 | impedance | LE16 |
| 3..4 | weight raw | LE16、通常値はraw / 100 kg |
| 5..7 | encrypted impedance | LE24 |
| 8上位4 bit | mode | parserはJavaの符号付きbyteを右へ4 bit shift |
| 8下位4 bit | 未解読 | parserでは参照しない |
| 9 | status | 0=安定、1=動的、2=過荷重 |
| 10 | checksum候補 | 旧記録ではbytes 0..9のXORと一致。アプリは検証しない |

modeは既知例では0です。bit 7が立つ値に対してアプリの式`data[8] >> 4`は
負数を返すため、無条件にunsigned 0〜15と同じ実装だとは記述できません。
名称から体組成モードと推定されますが、各コードの意味は未解読です。

### 安定・動的・過荷重

アプリの分岐は次のとおりです。

1. status=2なら過荷重イベントを通知します。
2. status=1ならraw / 100を動的体重として通知します。
3. status=0でもraw=65535（0xffff）なら過荷重イベントを通知し、安定測定を生成しません。
4. それ以外のstatus=0なら、重複抑制を経て安定値を通知します。
5. 0/1/2以外のstatusは、この経路では測定イベントになりません。

0xffffを常に655.35 kgへ換算して確定測定とする解釈は、アプリの安定値分岐と
一致しません。ただしアプリは動的値の分岐には同じセンチネル検査を行いません。
これを全status共通の挙動へ勝手に置き換えることも避けます。

### 重複抑制と測定モード

アプリは最後に受理した安定体重rawと時刻を保持します。
「前回受理から500 msより長く経過」または「体重rawが異なる」場合に受理します。
同一体重で500 ms以内の通知は除外し、除外時には時刻を更新しません。
impedance等を含むtupleの比較でも、最後の受信時刻との比較でもありません。

通常測定では体重raw、encrypted impedance、impedance、modeが結果になります。
抱きかかえ/ペットでは体重だけを扱う経路もあります。500 msは受信側の重複抑制であり、
BLEに同じ最小測定間隔がある証拠ではありません。

### checksumの確度

旧記録の11-byte通知はXOR規則と一致します。一方、確認した受信処理ではbyte 10を検証していません。
送信コマンドにXORがあることだけでは、受信checksumの必須規則を確定できません。
したがってXORは既存例で成立する規則として記録し、未確認の通知を同規則で
破棄してよいという意味にはしません。

## 履歴データ

| byte | 内容 | 解釈 |
| --- | --- | --- |
| 0 | type | cf |
| 1..2 | impedance | LE16 |
| 3..4 | weight raw | LE16、通常値はraw / 100 kg |
| 5..7 | encrypted impedance | LE24 |
| 8上位4 bit | mode | liveと同じ符号付きshift |
| 8下位4 bit | 未解読 | 未参照 |
| 9 | 未解読 | liveのstatusと同じ意味という証拠はない |
| 10 | 未解読 | liveのchecksumと同じ意味という証拠はない |
| 11..12 | 年 | BE16 |
| 13 | 月 | 暦日時 |
| 14 | 日 | 暦日時 |
| 15 | 時 | 暦日時 |
| 16 | 分 | 暦日時 |
| 17 | 秒 | 暦日時 |

受信parserは9/10を参照せず履歴recordを構成します。liveのstatus判定、0xffffの
排除、500 ms重複抑制はこの分岐にはありません。この違いはアプリの挙動であって、
履歴上の0xffffが正常な重量である証拠ではありません。

暦日時は受信端末のローカル時刻として解釈されます。
wireにUTC offsetがないので、旅行・時差・夏時間をまたいだ履歴の絶対時刻は
この配置だけでは一意に復元できません。

### 要求・完了・削除

確認した履歴転送の処理順は次のとおりです。

1. f2 00を送信して履歴を要求します。
2. CF/18-byteを履歴recordとして受信します。
3. f2 00通知で同期完了処理に入ります。
4. 1件以上の履歴recordを受信した場合だけf2 01を送信します。履歴0件なら削除要求を送りません。
5. f2 01通知で削除成功イベントが発行されます。

wireに件数、record ID、個別削除範囲があることは、この経路では確認できません。
f2 01は削除操作です。形式の記載は、受信recordを確認せず自動送信してよいという
要件ではありません。T9120の旧実測では履歴recordを取得できていません。

## その他の機能

safe mode、抱きかかえ、ペット、OTA開始の送信形式はコマンド一覧に含めています。

## 通信例と検算

### 旧実測記録

過去のT9120通信では、接続、FFF4の購読、初期化後のstable通知、f3 00と切断が
記録されています。個人の測定値と生通知は掲載しません。
元キャプチャファイルは再確認しておらず、各writeの成否やfirmware差も未確定です。
履歴要求に対する履歴recordの受信は確認できていません。

FFF1のproperties=8（Write）、FFF4のproperties=16（Notify）という記録があります。
過去の応答なしwriteの記述との違いは、原ログがないため確定できません。

## 未確認事項

- 各製品・firmwareでの同一コマンド対応、safe/baby/pet modeの実動作。
- 7-byte時刻の配置、14-byte時刻の2値の機器内での意味。
- f4応答、未使用status/mode、historyのbyte 9/10の意味。
- checksumの全受信形式に対する規則と、不正checksum時の機器側挙動。
- 履歴送出の条件・順序・最大件数・削除の範囲と永続化タイミング。
- kg/lb/st切り替え時の実際のwire scaling。
- encrypted impedanceと体組成算出の対応。数値フィールドの読出しだけでは未解決。
- 認証なしで取得できた旧T9120以外での相互接続試験。
