# AnkerScaleの設計

## 目的と現在地

体重計からBLEで測定値を取得し、Mac上のSQLiteに保存してCLIから参照します。
収集制御・解析・SQL・表示はMoonBitに置き、OS操作はObjective-CのC ABIで呼びます。
BLEヘルパープロセス、HTTPサーバー、RPC、GUIは設けていません。

収集・保存・CLI・常駐管理・Nixパッケージを実装しています。
既知パケット、接続状態遷移、GATT照合をMoonBitのテストで検証しています。
**実機受信と常駐ライフサイクルの実証は未完了です。**
[プロトコル](protocol.md)の過去の観測記録とは区別してください。

## 構成と責任

```text
launchd（ユーザーのLaunchAgent）
  └─ AnkerScale.app/Contents/MacOS/ankerscale service run
       ├─ MoonBit: 状態遷移、期限、解析、重複判定、SQL
       └─ Objective-C: CoreBluetooth、SQLite C API、macOS操作
              ↕ BLE体重計

収集プロセス ── 書き込み ── SQLite WAL ── 読み取り ── CLI
```

| ファイル・パッケージ | 責任 |
| --- | --- |
| `ankerscale.mbt` | T9120パケット解析、コマンド生成、整数体重の表示 |
| `collector.mbt` | 機器ごとの接続状態遷移、期限、再試行 |
| `collection.mbt` | 共有スキャン、登録の反映、機器へのイベント配送、全体停止 |
| `app/data.mbt` | スキーマ、トランザクション、rawと確定測定、重複判定 |
| `app/collection.mbt` | GATT照合、OSイベントと状態遷移の接続、収集ループ |
| `app/registration.mbt` / `app/registry.mbt` | 登録時の検索・選択・検証、登録形式、移行、一覧と解除 |
| `app/cli.mbt` / `app/service.mbt` | 引数、クエリ、出力、常駐操作 |
| `native/` | C ABI宣言とエラー変換 |
| `cmd/main/*.m` | CoreBluetooth、SQLite、ファイル、Service Managementの操作 |
| `resources/` / `flake.nix` | バンドル、LaunchAgent、ビルドと署名 |

ネイティブソースは、最終リンクとコンパイル設定を所有する実行パッケージに置きます。
MoonBitの `core/argparse`、`core/json`、UTF-8処理を使い、
外部MoonBitライブラリや汎用プラグイン基盤は追加していません。

SQLiteバインディングは必要なC APIを薄く包みます。
SQLとトランザクションの所有者はMoonBitです。
パラメーターをprepared statementに束縛し、読み取り専用接続を使い分けます。
NULLとエラーをMoonBitへ渡し、statementと接続は使用後に解放します。

## 機器とプロトコル

`register [--seconds 10]` で検索し、番号で選択した機器を収集対象に登録します。
スキャン時間は1〜300秒です。Bluetoothの準備を最大30秒待ち、
実際にスキャンを開始した時点から指定時間を数えます。
UUIDで広告をまとめ、検出した未登録候補へ直ちに接続します。
他の機器の検索を続けながら、候補ごとに名前・GATT構成・プロパティを確認して切断します。
短時間で電源が切れる体重計を扱うため、スキャン終了やユーザーの選択を待って接続しません。
検索期間の終了後も開始済みの確認と切断は完了を待ちます。
確認済み・登録済みの候補には機器名・UUID・RSSI・状態を付けてUUID順に並べます。
複数の番号はカンマで指定でき、空入力またはEOFは変更せず終了します。
1台だけでも自動登録せず、登録済みの機器は再接続・重複追加しません。

候補は名前が `eufy T9120` の機器と、名前不明で `FFF0` を広告する機器です。
名前不明の候補も接続後の名前とGATT構成で判定します。既知の未対応機種は接続対象にしません。
広告にサービスUUIDがないT9120も検索対象です。MACアドレスへは依存しません。

登録の検証では通知購読・初期化・測定保存を行いません。
確認結果はメモリに保持し、全接続を切断してBluetoothを閉じてから選択を受け付けます。
体重計がオフになっていても選択・一括保存でき、選択後には再接続しません。
機器ごとの接続・GATT確認の失敗は理由を表示し、その機器を選択対象から除外します。
GATT不一致では実際の名前・サービス・characteristicのプロパティも表示します。
接続とGATT探索は各10秒、切断は5秒で期限切れとし、自動再試行は行いません。
共有障害、切断期限切れ、中断では登録を変更せず、処理中の全機器をまとめて切断します。

初期化を許可するのは、名前が `eufy T9120` で、`FFF0` 内に
通知可能な `FFF4` と書き込み可能な `FFF1` がある機器です。
`FFF1` が応答なし書き込みに対応していればその方式を使い、
応答あり書き込みだけに対応する場合は応答ありで送ります。
T9146/T9147を含む他機種は候補のままで、互換性を推測してコマンドを送りません。
未知の機器では広告・サービス構成を診断情報として扱います。

通知購読の成功をMoonBit側で確認してから、200/600/1200 ms後に
kg設定・ローカル時刻同期・履歴要求を順に送ります。
履歴の削除コマンドは実装していません。
kg以外の設定でのwire-level scalingは未確認です。

## 登録一覧

登録一覧は収集対象の許可リストであり、測定DBの観測履歴とは独立しています。
保存先は `~/Library/Application Support/AnkerScale/devices.json` です。

```json
{"version":1,"devices":[{"id":"11111111-1111-1111-1111-111111111111","name":"eufy T9120"}]}
```

UUIDは検証・正規化し、重複UUID、未知の形式バージョン、不正なJSONはエラーにします。
登録変更には専用の `devices.lock` を使い、競合する登録操作は待たずに拒否します。
ファイルは原子的に置き換え、新規ファイルはユーザーだけが読める権限にします。

`devices [--json]` はBluetoothを開かず一覧を読みます。
`unregister` は番号で選択した登録だけを解除し、測定DBには書き込みません。
`devices.json` がないときだけ旧 `service.json` の単一UUIDを読み、
次の登録変更または `service start` で新形式へ移行したことを表示します。
新形式の空一覧から旧設定へ戻ることはありません。

収集は約1秒ごとに再読込し、追加した機器を待ち受け対象に加えます。
解除した機器は新規接続・初期化を止め、受信済みデータを保存して切断します。
他の機器の接続は維持します。全台解除後はスキャンを止め、新しい登録を待ちます。
稼働中に設定が壊れたり消えたりした場合は、空一覧や旧設定へ置き換えず、
エラーとして全接続を停止します。

## BLEの実行順序と停止

CoreBluetoothのオブジェクトは専用の直列キューに閉じ込めます。
OSコールバックではMoonBitオブジェクトを作成・操作しません。
値を所有するイベントをキューへ入れ、MoonBit側がC ABI経由で取り出します。
受信時刻と単調時計はコールバック時に取得します。
制御の期限はMoonBitがイベントを処理した時点から計算します。

- 通知購読が成功するまで初期化writeを送りません。
- UUIDと接続試行番号を照合し、古いコールバックで次の接続を進めません。
- 接続試行番号は収集実行内で一意に割り当て、解除後の再登録でも再利用しません。
- 接続、GATT探索、通知購読の期限はそれぞれ10秒です。
- 測定中は受信が30秒ない場合、または購読から120秒が経過した場合に切断します。
- 再試行待ちは1秒から30秒まで増やし、受信できたら戻します。
- 切断完了を確認してから再検索します。キャンセル完了の期限は5秒です。
- 停止要求を優先し、新しい接続・初期化を止めます。
- 終了時には受け渡し済みのイベントを保存してからDBと書き手ロックを閉じます。

共有のスキャンと、機器ごとの接続制御を分けます。
Objective-C側もdelegate・characteristic・送信待ちを接続ごとに保持します。
機器単位の接続失敗やプロファイル不一致は他の機器へ波及させません。
キャンセル完了を確認できない場合は、全体の整合性を保てない障害として停止します。
全体停止では同時にキャンセルを要求し、機器数によって期限を延長しません。

初期化間隔と重複判定は観測メモを基にしています。
その他の期限は停止・復帰の上限を明確にする実装値であり、
実機での取得成功率や最適な待機時間を証明するものではありません。
スキャンは検索待ちの機器がある間だけ継続します。
一方への接続開始によって、他方を探すスキャンを停止しません。
重複広告の通知は抑制し、再試行や機器追加時にはスキャンを更新します。
これは[CoreBluetoothの重複検出抑制](https://developer.apple.com/documentation/corebluetooth/cbcentralmanagerscanoptionallowduplicateskey)
によって再発見が止まることを避けるためです。

イベント待機はセマフォを使い、1秒を上限として停止要求も確認します。
受け渡しキューは1024イベント、探索キャッシュは512機器、
書き込み待ちは機器ごとに16件までです。
共有イベント・探索キャッシュの上限超過は全体停止、送信待ちの上限超過は対象機器の接続エラーです。
バックプレッシャー中のwriteはネイティブ側で順序を保ち、切断時に未送信分を取り消します。
応答ありwriteは完了コールバックを待ってから次を送信し、エラー時はその機器を切断します。

保存に失敗した場合も収集を止めます。
すでに取り出した未保存イベントとOS側に残るイベントを標準エラーへ報告します。
ディスク障害時にログまで永続化できることは保証しません。

## 保存と測定の意味

既定の保存先は `~/Library/Application Support/AnkerScale/records.sqlite3` です。
新規ディレクトリは0700、DB・ロック・ログはユーザーだけが読める権限で作成します。
同じDBの通常の書き手は一つとし、プロセス間ロックで二重収集を拒否します。
CLIの参照には書き手の稼働を必要としません。

| テーブル | 保存する情報 |
| --- | --- |
| `devices` | ホスト内識別子、名前、観測したサービス、初回・最終検出時刻 |
| `raw_packets` | 実行・接続・連番、送受信方向、UTC受信時刻、単調時計、GATT、hex、出典、解析版・種別・エラー |
| `measurements` | 元のraw、整数体重、測定フィールド、端末の測定時刻 |
| `events` | 接続状態、広告・GATT情報、エラー、開始・停止などの診断 |

rawと、そこから得られる確定測定は同じトランザクションで保存します。
安定値以外、checksum不一致、未知の通知、18 bytesの未確認履歴候補は、
確定履歴には追加しません。rawには残します。
送信rawはwriteをOSに渡した記録であり、端末が適用した証明ではありません。

同一実行・同一機器で、直前の安定通知から500 ms未満かつ
体重・impedance・encrypted impedanceが一致する場合は確定測定を重複させません。
重複rawは保持します。途中に動的値や過荷重がある場合、または500 ms以上離れた場合は
別の測定として扱います。接続をまたぐ再送も同じ実行内で評価します。
再起動後や別のreplay実行は別の実行として扱います。

体重の単位は整数の0.01 kgです。
live packetには日時がないため `measured_at` はNULLとし、
表示や期間検索にはUTCの `received_at` を使います。
不明な端末日時を現在時刻で補いません。

DBはWALと `synchronous=FULL` を使用します。
参照コマンドは読み取り専用で開き、別アプリのDBや未知のスキーマを拒否します。
exportは一つの読み取りスナップショットから500件ずつ出力し、終了時に閉じます。
raw・診断ログの自動削除は行いません。保持期間は実運用の保存量を測って決めます。

## CLIの契約

- `register` は検索と追加登録、`devices` は登録済み一覧、`unregister` は選択解除です。
- `devices --json` はUUIDと名前を持つオブジェクトの配列を返し、未登録時は `[]` です。
- `collect [--db PATH]` と `service start` は登録済み全機器を対象にします。
  未登録で開始すると引数エラーで `register` を案内します。
- `collect` と `service start` の `--device`、`devices` の `--seconds` は受け付けません。
  `history` / `export` の `--device` は検索条件として維持します。
- `latest` は受信日時が最も新しい1件を返します。
- `history` は受信日時の降順で既定100件を返します。`--limit` は1〜10000です。
- `export --format csv|json` は条件に合う全件を受信日時の昇順で出力します。
- `--since` は境界を含み、`--until` は含みません。
- 日時は `YYYY-MM-DD`、UTCの `YYYY-MM-DDTHH:mm:ssZ` またはミリ秒3桁付きです。
  日付だけの場合はUTCの午前0時です。UTC以外のオフセットは受け付けません。
- JSONのlatestはオブジェクトまたは `null`、history/exportは配列です。
  空の履歴は成功として扱い、人向けには `No measurements.` と表示します。
- 測定出力のキーは `id`、`device_id`、`received_at`、`measured_at`、
  `weight_centi_kg`、`impedance`、`encrypted_impedance`、`fat_mode`、`origin`、`raw_id` です。
- CSVはヘッダー付きで同じ列を使い、NULLは空欄、文字列は引用・エスケープします。
- `logs` はrawと収集イベントを合わせて新しい順のテキストで表示します。
  `logs --json` は `source`、`received_at`、`kind`、`detail` を持つJSONLを返します。
- `--db` は収集・記録参照・replayで指定できます。常駐収集は既定DBを使います。
- 通常の結果は標準出力、診断は標準エラーへ出します。
- 終了コードは成功が0、実行・保存エラーが1、引数エラーが2です。
  DBが存在しない場合も読み取り専用のままエラーにし、空のDBを作りません。

`replay FILE.jsonl --db PATH` は明示的なオフライン入力です。
実際の収集と同じ保存経路を使いますが、出典を `replay` として記録します。
テスト用の別DBを指定してください。同じファイルを再実行すると別実行として追加します。
途中で失敗した場合は、それ以前にコミットされた通知は残ります。

## 常駐と権限

`~/Library/LaunchAgents/com.ph0ryn.AnkerScale.collector.plist` を生成し、
`launchctl bootstrap` でユーザーのLaunchAgentを登録します。
実行するバンドル内バイナリの絶対パスを `Program` に保存します。
旧 `SMAppService` 登録は個別に解除して移行します。
macOS 27で旧方式の起動制約がビルド更新後に残り、起動を拒否するケースを実機で確認したためです。
システム全体のBTMリセットやDeveloper ID証明書は必要ありません。
`service start` は登録一覧を検証して常駐を登録します。
稼働中の機器追加・解除には再起動を必要としません。
`service stop` はlaunchdの対象ジョブへSIGTERMを送り、
書き手の終了を最大10秒待ってから登録を解除します。
終了を確認できない場合はエラーにし、強制終了で成功扱いしません。
`service stop` は機器の登録一覧を削除しません。
停止後は `launchctl bootout` と生成したplistの削除を行います。
ビルドを更新した場合は一度停止してから起動します。稼働中の登録先変更はエラーにします。
同じビルドへの再度の `start` は、稼働中のプロセスを維持します。
全台解除後にlaunchdが再起動した場合も、内部の `service run` は空の登録一覧で待機できます。

LaunchAgentはログイン中だけ動き、異常終了時には間隔を置いて再起動します。
rootのLaunchDaemonは使用しません。
`service` と `logs` は既定で人向けのテキストを表示し、`--json` で従来の構造化出力を返します。
`service start` と `service stop` の通常出力は完了結果の1行だけです。
`start` は `launchctl kickstart -p` のPIDとwriterロックのPIDが一致し、
そのPIDの `started` イベントが記録されるまで最大10秒待ちます。体重計の接続は待ちません。
`stop` は保存終了後に登録解除し、writer不在と登録解除済みを確認して成功を返します。
停止・登録解除・最終確認の各待機にも10秒の期限を設けます。
承認待ち・定義欠損・時間超過は成功扱いにせず、次の確認手順とともにエラーを返します。
`service status` と明示的な `--json` では詳細な状態・履歴を参照します。
収集中の通常診断は日時付きのテキスト、DBの診断は構造化データとして保存します。
保存失敗時の未保存イベントは、復旧に必要なJSONを診断ログへ残します。

`service status` は登録状態、書き手ロック、最後の保存、最後の診断を分けて表示します。
`devices` には機器ごとの `phase`、時刻付きの `last_state` と `last_error` を返します。
状態は既存の `state` / `device_error` イベントから読み、書き手がいなければ `Inactive` とします。
`started` のPIDと現在の `writer_pid` が一致する実行の状態だけを現在値として表示し、
書き手が別プロセスの場合は `Unknown` とします。
過去の状態・エラーは診断用に残し、最後のエラーがあることだけで現在の故障とは判断しません。
書き手ロックは前面収集やreplayでも保持されるため、常駐サービスだけを表すものではありません。
最近の記録がないことだけで故障とも判断しません。

バンドルの識別子は `com.ph0ryn.AnkerScale` です。
Nix出力ではad-hoc署名とBluetooth用途説明を含めます。
CLIの入口はバンドル内の実行ファイルを起動し、NSBundleの識別を保ちます。
Developer ID署名・公証、権限の帰属、更新時の引き継ぎ、実際のサービス登録は
自動テストで確認していません。

スリープ中やログアウト中の取得は保証しません。
単調時計にはスリープを含む `mach_continuous_time` を使いますが、
実際の復帰とBluetooth再接続、待機時のCPU・メモリ・消費電力は実機確認が必要です。
